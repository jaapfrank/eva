# EVA1/EVA2 product baseline and decision constraints

Research date: 27 September 2026. Integration basis: `c025550b618644f19591dd6ad987420252915771`. One bounded evidence pass, not a repository audit, new benchmark, release decision or recommendation to replace the installation. See [read register](baseline-sources.json). The coordinator owns synthesis and the only workboard.

## Decision-relevant conclusion

EVA2 has reusable, partly owner-accepted assets, and recent deliveries have overtaken several August comparison claims. The available evidence nevertheless does not establish that EVA2 is a better complete daily product than EVA1, or faster, more intelligent or more autonomous than competing systems. EVA1's valued presence is part of the baseline, not merely historical code to discard. EVA2's strongest assets are personal continuity, explicit household/private separation, durable task/effect records and controlled delivery to the original destination. Its demonstrated weaknesses concern complete multi-step tasks within the actual execution contract, integration across real user entrances, and the context and coordinator intervention required.

The runtime already uses Pydantic AI. Selecting that framework again is not itself a solution. A full agent platform is a legitimate alternative, but neither its migration value nor the value of retaining the present execution arrangement has been established by equal task comparison. Preserve accepted outcomes and data; make the later architecture choice answer the whole [product goal](../../PROJECTDOEL.md), including optional replaceable modules and general digital work.

## Evidenced causes of repeated work

1. **The task contract is narrower than framework availability.** `PydanticConversationModel` calls real `Agent.run()`, explicitly limited to one request/one tool call per invocation. `LivingConversation` owns the surrounding loop; `DelegatedDigitalRunner` adds persistence, progress, task context and attempt limits. Current candidate defaults remain six tool actions/eight model responses. The [27 September review](../../evidence/product/digital-task-budget-candidate-20260927.json) finds the observed initial learning path needs at least eight actions/nine responses. Passing reader/budget tests cannot close this full-path mismatch. It does not prove a framework change necessary or sufficient.

2. **Installed user chains cross independently built boundaries.** The [21 September review](../../reviews/reassessment-evidence-2026-09-21.md) traces document activation through missing composition, worker/effect endpoint, private RPC identity and healthchecks. Recent board entries add core/worker release mismatch, citation parsing and result presentation after admission already worked. Complete outcome/composition must be assessed together; individual green components do not establish it.

3. **Per-turn policy became task policy.** The [external learning receipt](../../evidence/product/external-documentation-learning-source-only-20260925.json) records a per-response input limit also serving as the cumulative task cap, local reader errors and explicit resumes. The uninstalled 27 September patch separates dimensions/batches selection but leaves the full-path limits unresolved. This explains partial repairs; it does not justify unlimited work.

4. **Context and repeated model transitions have observable cost.** External learning recorded 75,450 input tokens in the initial reviewed attempt, before resumes, without a saved/executed procedure. The harmless HA task recorded 108,076 input tokens and 10 responses/attempts with coordinator resume. Successful reuse still recorded 43,262 input tokens. Worker accounting is partial: these are recorded subtotals, not full billing. Repeated context is plausible from loop structure; a causal per-component attribution or saving estimate requires traces. No reduction can be assumed from a platform switch.

5. **Receipt and content latency differ.** [Website proxy evidence](../../evidence/product/local-owner-receipt-flush-installed-20260925.json) gives one receipt delay 4.853→0.036 s; after-case content at 2.091 s. This establishes header buffering correction, not model speedup. Research admission took 12.871 s while an overlapping simple answer began at 2.779 s. [Pinned HA analysis](../../evidence/product/ha-short-receipt-boundary-20260925.json) finds no supported short-segment flush in HA 2026.9.2, and announce cancels the active pipeline. A short-response regex cannot prove immediate physical receipt. Current upstream findings belong to the coordinator's separate research.

6. **Historical present-tense language causes false work or completion.** August pages still say no voice/speakers or Pydantic 2.32.1; current receipts/fingerprints contradict them. Conversely installed household initiative is not yet audible/useful evidence. Old “now/next” board entries remain history. Checker/line counts are not runtime defects or cleanup mandates.

Many past reviews found real defects, so removing review loses valuable detection. Bundle it around a complete bounded outcome, rerun only changed causes, and keep source/install/acceptance separate. These findings are research input, not a new repair queue.

## Retention and migration principles

Preserve **outcomes and information**, not a whole implementation automatically: accepted memory/conversation, valuable EVA1 presence, both general HA speaker bindings, private Telegram, original task/effect history, cancellation, destination binding and uncertain-effect readback. Chosen optional user scope remains chosen.

For every major responsibility, the later proposal should state retain/connect/replace, expected user improvement, affected code/data, the component that would own it, which old active route disappears, and equal task evidence that could disprove the choice. Framework feature lists and line savings do not establish product value. The distinctive hypothesis is one recognizable family housemate combining conversation, memory, initiative, home and digital work while staying private, fast and useful; assess that combination.

Make optional modules explicit: dependencies, identity/audience interfaces, exportable canonical data and meaningful behavior when absent. Avoid permanent duplicate planners, dual-writing personal memory, or an executor owning a second task truth. Preserve old effect records rather than replaying actions into the new engine. A new general execution platform is not ruled out; replacing the current execution engine may be preferable to further extending its custom loop if whole-task evidence and migration costs support it.

Do not require a full benchmark before every choice. First compare complete system alternatives using this baseline and current upstream evidence, expose migration/maintenance uncertainty, then derive one coherent proposal. Later authorized work should use the smallest decisive end-to-end cases under EV-003 and actual physical entrances where relevant. No candidate installation, learning repair or trial belongs to this research pass.
