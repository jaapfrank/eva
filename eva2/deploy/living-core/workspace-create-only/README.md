# Bound create-only broker candidate

This is an isolated provider primitive, not an activated MCP provider. It reuses
`native/workspace_writer_broker.c`; there is no second receipt database.

## Wire and durable identity

`EVWWREQ2` retains v1 fields through byte 89, inserts a nonzero 32-byte
`request_binding_sha256` at byte 90, then the path and UTF-8 content at byte 122.
The binding must be generated by the host from its versioned goal/plan/step,
previous artifact, configuration, path and content contract. The broker treats
it as an opaque exact binding, not as authority. The existing full-frame SHA
in EVWWRCP1 binds this field, generation and content. Journal and receipt
formats stay v1; ordinary all-v1 requests retain their behavior. V2 accepts
one request only, including when mixed with v1 frames.

The caller pins `operation_id`, `expected_generation` and the complete request
before dispatch. Reusing an operation with a different frame is a conflict.
The client validates receipt checksum, full request hash, identity, path,
content hash/length and generation, returning the supplied binding only after
those checks. It accepts host-owned directory FDs and executable; it does not
open arbitrary roots, mint authority or map untrusted tool fields to FDs.

## Execute versus observe

Execution retains O_TMPFILE/linkat create-only publication and never replaces
conflicting content. Existing identical content can yield the existing `noop`
receipt; that is not a claim that this operation created the file.

`--observe` opens an existing journal read-only and takes the existing exclusive
lock. It never calls pending recovery, fsync, publication, or journal append.
Committed C receipts are returned after existing file/inode/content validation.
A durable L publication record can yield the identical receipt in memory without
writing C. P-only or the crash window after link but before L stays uncertain;
observation must not repair it. Missing, changed or ambiguous effects fail.

V2 execution refuses to recover an unrelated pending request. An exact execution
retry may recover under existing broker rules; observe never does. This does
not remove the existing ambiguous post-link/pre-L recovery boundary.

## Verification and remaining integration

The targeted suite combines the existing v1/native checks with v2 crash barriers,
changed request/file rejection, missing-journal observation, concurrent creator
preservation and client receipt validation. All filesystem effects use temporary
private fixture directories. No model, live workspace, service or deployment is
used.

Before AU006 can use this in production, the host must bind the plan to real
McpOwnerAuthority and current mandate/stop checks, compose a narrowly scoped MCP
catalog/effect/observe route, provision isolated root/journal FDs and prove DAC
and lifecycle behavior. These are not supplied or claimed by this candidate.
No security claim rests on UUID secrecy or read-before-write. The native code is
repository-owned existing code; deployment must pin the reviewed source/binary
and rerun the appropriate existing native checks when its version changes.
The maintained upstream filesystem provider is retained for its existing tools;
its overwrite-capable write_file is not used to promise immutable receipts.
## Host lifecycle contract (candidate, not deployed)

Provision one host-owned private journal per approved project. The two-step
plan pins generations 0 and 1 in its exact durable requests; do not guess a
shared global generation or advance it after a conflict. Keep the same journal,
operation ID, binding and request across restarts. No bridge receipt journal is
introduced here.

`runBrokerResult` returns either `receipt` (with explicit created/noop effect)
or `blocked` (bounded code). In particular operation_not_found, missing journal,
uncertain pending effects, conflicts, malformed receipts and process failures
never mean that executing again is safe. The adapter has no automatic retry.
A noop proves availability under the existing receipt semantics, not this
operation's creation; a create-specific acceptance test requires created.

`initialNone` is exclusively a host lifecycle decision based on durable proof
that this exact operation has never been dispatched, before marking dispatch
started. It is not produced by this adapter or inferred from journal absence.
After dispatch started, absence or uncertainty blocks; only observation of a
verified receipt can complete recovery. Although the native legacy protocol can
recover on an exact execution retry, this project bridge must not use that as an
observation fallback. Provisioning and dispatch admission must be bound to the
same host authority and durable plan lifecycle before production use.
