# R1: bounded executable experience comparison

Decision question: can a learned advisory transition predictor improve adaptation to changed assumptions beyond an ordinary reusable method, current observations and full sequence validation on a copy? This implements the existing optional R1 research task, not a new product planner or benchmark platform.

The synthetic reservation service has no production data, network tools or house effects. Both arms use the same existing Astra/medium subscription route, ordinary method, service contract and result/readback requirements. Only the predictor arm receives `simulate_plan`; generated code runs in Eva's existing offline procedure executor. A separate Sol/none contact call receives no private work history. The installed core is the host for the existing provider and executor, not the system being scored as a complete product.

The independently curated two cases each have two episodes. Each case/arm is repeated twice, with balanced order. Curator-owned inputs and scoring remain outside the repository until the source and candidate are frozen. Fixed criteria are in `criteria.json`; model usage includes both synthesis attempts. Construction failures and validator corrections remain in `construction-evidence.json`. The generated predictor is unchanged after synthesis. Requested model aliases and exact available image/library/source provenance are recorded; underlying provider weight revisions are not exposed.

`generate.py` synthesizes the ordinary method and predictor from the public contract and development observations. `validate.py` checks the generated source against development transitions through the existing executor. `wire_check.py` checks SDK continuation locally without provider traffic. `guard_check.py` checks immediate stop and harmless cached replay. `compare.py` runs the frozen comparison and preserves partial results on failure; no automatic retry or promotion occurs.

The optional experiment response/tool/token ceilings are declared before execution. Provider output is accounted after completion, so an output overrun invalidates the round and stops further calls; a strict pre-transport output-token ceiling is not available on this route. Four eligible uses are represented per repeat block, so this experiment cannot establish amortized savings over the required five-use horizon. Successful predictions alone are not actual task outcomes. Credit prices and developer-assistant token use are not inferred from experiment token counters.

Existing JSON Patch copy execution and ordinary skill reuse are prior working capabilities, not this candidate's novelty. The existing research already identifies executable-model prior art including Twin. Neither a successful local development check nor this bounded decision establishes original AIDE/AIDE² reproduction, competitor superiority, global novelty, family acceptance or a complete new product function.

Execution and independent grading have not yet completed. Do not install a candidate without meeting the existing promotion conditions. A loss, tie or incomplete round is retained without silently expanding the research scope; meaningful technical distinction remains a separate open product requirement.
